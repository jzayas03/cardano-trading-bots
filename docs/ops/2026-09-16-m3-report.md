## Verdict

**M3 met against spec §8, for runs 147 (ma-crossover) and 148 (buy-and-hold).** Both ran
continuously from 2026-09-09 00:15 UTC to 2026-09-16 11:24 UTC — 7 days 11 hours — on SNEK, with
717 equity points each, 100% coverage, zero unpriced points, and one resume each whose history is
intact. Each day's report cites the run id, the git sha, the fills and the costs.

**The third strategy, rsi-mean-reversion, did not run 7 days under one run id.** It is run 146
(2026-09-09 00:15 to 2026-09-11 06:16, 217 points) plus run 149 (2026-09-11 06:16 to 2026-09-16
11:24, 501 points). The history is complete across the two rows (218 points at the restart against
237 for the continuous runs, see §4); the identity is not. The spec bar does not say one run id, so
this does not fail M3, but it is stated here rather than hidden in a compare table that lists 149
alone.

Qualifications the runbook adds beyond the spec, and which this run did **not** satisfy:

1. **The daily reports were not taken daily.** They were regenerated from the database at the end
   (§3). The runbook says a week reconstructed at the end is not the same artifact; that is
   accepted. The numbers are the same numbers, because `report --day` reads persisted rows.
2. **The two day-2 drills were not performed** (§4). The only restart in the week was the
   unplanned one of 2026-09-11 06:16:42, which exercised the clean-restart path for 147 and 148 and
   the fork defect for 146. The crash-recovery path (stale heartbeat after `kill -9`) was not
   exercised at all on this week's runs.
3. **Four of six preconditions have no recorded evidence** from the day the runs started (§2).
   `doctor` was run for this report instead, a week late, and is OK with one warning.
4. **The one-sha invariant holds in substance, not in letter** (§7). Rows 147/148 say `06b2893`,
   row 149 says `0d42901`, and after the 09-11 restart all three processes ran `0d42901` code.
   Nothing under `packages/paper`, `packages/strategies` or `packages/sim-executor` differs between
   the two shas, so the equity curves came from identical code.

**This is a plumbing check, not a strategy result.** Every profit-and-loss figure in this report is
one week, one token, one pool, fills against observed reserves with one venue's costs assumed. The
promotion gate bars all three strategies (ma-crossover 8 of 30 round trips, rsi-mean-reversion 4 of
30, buy-and-hold is a baseline). Nothing here is evidence that any strategy clears its cost floor;
see `docs/ops/2026-09-09-strategy-state.md` for why that question needs a different measurement.

## 4. The drills — not performed as drills

The runbook prescribes two drills on day 2 (2026-09-10): a clean restart (SIGINT, confirm
`finished`/`signal`, resume, confirm `seq` continues and `params.resumes` gains a timestamp) and a
crash recovery (`kill -9`, confirm the row stuck at `running` and the heartbeat STALE, resume through
the stale-heartbeat path). It also warns that `Restart=always` on `ctb-paper@.service` relaunches the
unit before a manual `--resume` can run, and that on a deployment older than #113 the relaunch forks
a cleanly stopped run.

**Neither drill was performed.** The systemd journal for 2026-09-09 to 2026-09-12 (Appendix C) has
exactly one event after the runs started: at **2026-09-11 06:16:42 UTC** all four units — the
collector and the three paper runs — were stopped and started together. No reboot occurred in the
week. `docs/ops/2026-09-09-strategy-state.md` records it as "deliberate, not a crash
(`NRestarts=0` on all four), not a deploy".

What that one event proved, from the run rows and the full reports:

- **147 and 148 resumed.** `params.resumes` gained `2026-09-11T06:16:47Z`; the full reports carry
  `warning: resuming a run whose heartbeat is still fresh (age 47s) but which no process was
  running; the previous process died without recording a stop` and `warning: resumed ... intents
  pending at the previous stop were lost`. Equity points are continuous across the restart
  (query 2, §5: 96 points on 09-11 for both). The `seq` half of the clean-restart assertion is
  meaningful for 147 (6 fills before, 11 after); for 148 it is vacuous (one fill, on day one).
- **146 forked into 149.** 146 wrote `finished`/`signal` at 06:16:42.386; 149 was created at
  06:16:47.293. This is the race PR #113 closed the same day (`infra/vps/resume-target.sql`): the
  outgoing process flushed its clean stop within five seconds, so the incoming one found no running
  row and started new. History: 146 has 217 points, 149 had 21 by the time the note was written
  and 71 by the end of 09-11; 147 and 148 have 96 for that day. Nothing was lost; the identity was.
- **The stale-heartbeat crash path was not exercised** on any run in this week. The 09-11 resume
  went through the fresh-heartbeat, no-process path, which is the opposite branch.

So the restart drill happened by accident, on the wrong day, in the form of the exact defect the
runbook's caveat describes, and the crash drill did not happen at all. The runbook's own guidance
(`systemctl stop` the unit first, then drill) was written after this, in PR #118, because of this.

## 7. The one-sha question

The runbook says "A week's equity curve has to come from one git sha" and treats `0d42901` as "the
sha the week actually ran on". The rows disagree with the letter of that:

- `runs.git_sha` is `06b2893` for 146, 147 and 148 (created 2026-09-09 00:15 UTC) and `0d42901`
  for 149 (created 2026-09-11 06:16 UTC). `06b2893` is the merge of #84 (2026-09-08 22:45 UTC);
  `0d42901` is the merge of #89 (2026-09-09 13:30 UTC).
- `deploy.sh` runs `systemctl enable --now`, which does not restart an already-running unit. So the
  `0d42901` deploy on 09-09 left the three processes running `06b2893` code from memory, and the
  09-11 06:16 restart is the moment all three began running `0d42901` — while rows 147 and 148
  kept the sha they were created with. From then on their sha column describes the row's origin,
  not the code that wrote its later points.

In substance the invariant held: `git diff --stat 06b2893 0d42901 -- packages/paper
packages/strategies packages/sim-executor packages/cli/src/commands/paper.ts` is empty. The five
commits between them touch external-candle denomination, backfill/backtest, the watchdog, `doctor`
and migration 0008. The only `feeds.ts` change is to `externalCandleFeed`, the backtest path. The
paper loop, the strategies and the fill model that produced every point in this report are
byte-identical across the two shas.

What this means for the next week: `runs.git_sha` cannot be read as "the code that ran"; a resume
should record the sha it resumed under, or the deploy should refuse while paper units are active.
Follow-up, not fixed here.
